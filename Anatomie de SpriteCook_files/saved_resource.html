§1Ce qu'est le produit

SpriteCook n'est pas un générateur d'images. C'est une couche de contraintes métier et d'orchestration posée sur des modèles d'images génériques, dont la valeur est presque entièrement dans ce qui se passe avant et après l'appel au modèle.

Couche 4Surfaces
Application web (11 écrans), API REST api.spritecook.ai/v1/api, serveur MCP (43 outils) branché sur Claude, Cursor, Codex, OpenCode, VS Code. Les trois surfaces attaquent le même compte et le même solde de crédits.
Couche 3Workflows guidés
Assistants multi-étapes qui transforment une intention floue en une séquence de générations chaînées : personnage + set d'animations, kit d'interface complet, tileset autotile, pack de démarrage par genre.
Couche 2Contraintes & post-traitement
Le cœur de la valeur. Alignement sur grille pixel, quantification de palette, détourage, recadrage intelligent, découpe par alpha connexe, assemblage en atlas autotile, détection de bordures 9-slice, mise en spritesheet.
Couche 1Modèles d'images
Cinq modèles tiers, exposés tels quels : Gemini 2.5/3.1/3.1-Lite/3-Pro Flash Image et GPT-Image-2. Aucun modèle propriétaire. Le modèle d'animation, lui, n'est pas exposé.

Conséquence pour un projet similaireReproduire la couche 1 est trivial (des clés d'API). Reproduire la couche 2 est le vrai travail : c'est là que se logent le « pixel perfect », les atlas qui tuilent réellement, les 9-slice exploitables. La couche 3 est ce qui fait la différence de conversion, parce qu'elle empêche l'utilisateur de se perdre.

Le vocabulaire du produit

Asset
L'unité atomique : une image fixe ou une animation, toujours détenue par un compte.
Pixel / Detailed
Les deux univers de rendu. pixel=true déclenche tout le post-traitement grille ; pixel=false produit du HD lissé.
Crédit
L'unité de facturation. Chaque bouton qui en consomme affiche son coût exact avant le clic.
Job / Run
L'unité asynchrone. Un run regroupe plusieurs jobs (un set d'animations).
Preset
Un jeu de réglages sauvegardé et partageable — le mécanisme communautaire du produit.

Auto-provisionnement : le détail le plus intelligent du modèle

Les workflows guidés ne se contentent pas de produire des assets : ils créent le rangement en même temps. L'utilisateur n'organise jamais rien à la main, et pourtant sa bibliothèque reste structurée.

Règles d'affectation

  • Affectation atomique, jusqu'à 500 assets par opération.
  • Sortir un asset de son projet efface aussi son appartenance à une collection.
  • Sortir un asset d'une collection ne touche pas à son projet.
  • Affecter un asset à une collection imbriquée dans un projet le déplace implicitement dans ce projet.

Un seul écran, quatre types de génération, un panneau de réglages qui se recompose selon le type choisi. C'est la pièce la plus dense du produit.

Le bloc « Theme & Style », replié par défaut

  • Onglet Theme — un champ libre pour l'univers du jeu (« Medieval High Fantasy, Cyberpunk City… »), avec deux boutons : Random et Refine.
  • Onglet Style — un sélecteur de preset visuel à deux familles (Pixel Art : 8-Bit, 16-Bit, Modern, Dark, Chibi, Isometric… / Detailed), ou un champ libre de direction artistique.

La séparation prompt / thème / style est structurante : le prompt décrit l'objet, le thème décrit le monde, le style décrit le rendu. C'est ce découpage qui permet de garder une cohérence entre des assets générés à des semaines d'intervalle.

§5Les huit parcours

Tout le produit se ramène à huit parcours. Trois sont des assistants multi-étapes, cinq sont des formulaires uniques.

5.1 · Prompt universel routeur

Sur l'accueil, un champ unique avec un sélecteur Auto. En mode Auto, SpriteCook classe l'intention et route vers le bon outil ; l'utilisateur peut forcer la destination (Assets, Character, Tileset, Texture, Animation). Un bouton d'historique de prompts et un ajout d'image de référence complètent la barre.

5.2 · Asset Generator formulaire

Le parcours par défaut : réglages à gauche, prompt + champ Avoid (prompt négatif) au centre, bibliothèque en dessous. Chaque asset de la bibliothèque porte quatre actions de réinjection — Use (reprendre ses réglages), Ref (le passer en référence), Edit (le passer en source d'édition), Style (le passer en guide de style) — plus Open editor. C'est le mécanisme de cohérence visuelle du produit : on ne repart jamais de zéro.

Trois détails de conception méritent d'être relevés.

a. La perspective verrouille tout

Une fois le sprite de base généré, le jeu d'animations est LOCKED sur la perspective choisie. Cela évite l'incohérence classique (un personnage de plateforme à qui on demande un « walk up ») et réduit drastiquement l'espace de choix.

Frames par animation : 8 pour idle / walk / jump / attack / hurt, 10 pour run, 12 pour death.

b. Le mécanisme de « prep » — la vraie astuce technique

Un modèle d'image ne sait pas animer un personnage vu de face pour le faire marcher de dos. SpriteCook insère donc, entre le sprite de base et l'animation, des générations intermédiaires de pose : le sprite de base est d'abord retourné ou remis en pose (« Turn this character around », « Put him in a walk pose »), et c'est ce sprite préparé qui sert de source à l'animation.

  • Chaque prep est un asset visible dans la bibliothèque — j'ai vu apparaître Character Walk Pose Prep pendant le test.
  • Coût : 12 en pixel, 2 en detailed.
  • Certaines preps se chaînent : la marche de dos dérive de l'idle de dos, pas du sprite de face. Le graphe de dépendances est déclaré côté serveur, animation par animation.
  • L'interface signale d'un pictogramme les animations qui déclencheront une prep, et lance une phase « Analyzing character… » pour déterminer si la pose de départ est déjà exploitable.

c. La remise au volume et le cadrage

Le prix affiché baisse quand on coche plus d'animations : sur mon test, 3 animations passent de 72 à 60 avec la mention « Batch discount active ». Le panneau latéral affiche la transformation de cadrage (53×71 → 80×80) et offre : marge 0–25 %, marge de sécurité, forçage en puissance de 2, et une grille 3×3 d'ancrage. Le détourage se choisit entre Basic et Pro +2/frame. Deux options fines : Set up starting poses et Edit motion prompts.

d. Le playground

L'écran final n'est pas une grille de fichiers : c'est un mini-jeu jouable où le personnage marche, court et saute au clavier, avec cinq curseurs de physique (walk, run, jump, gravity, FPS). C'est la meilleure idée d'UX du produit — l'utilisateur valide ses animations en contexte de jeu avant d'exporter.

La taxonomie des composants extraits

C'est le point le plus réutilisable du produit pour qui voudrait s'en inspirer. Chaque pièce détectée reçoit un rôle, un état, et un drapeau d'étirabilité. Relevé sur un kit réel de 31 éléments répartis en 9 groupes d'états :

RôleÉtats observésÉtirable
FRAMENORMAL · HOVER · PRESSED · DISABLED9-slice, ou fixed pour les variantes pleines
BUTTONNORMAL · HOVER · PRESSED · DISABLED · SELECTED · UNSELECTED9-slice
DIVIDERNORMALfixed
FILLFILL9-slice — la partie mobile d'une jauge
ICONON · OFFfixed

Le regroupement par state group permet d'éditer les quatre états d'un même bouton en une seule action. L'éditeur 9-slice affiche un aperçu d'étirement en direct (« drag the handles to stretch or squash ») pour valider les bordures avant l'export.

La continuité entre écrans

Une fois un kit terminé, SpriteCook propose directement : « What screen do you need next? ». Le style, le projet et le concept sont conservés comme référence pour le kit suivant. C'est le mécanisme qui transforme un outil de génération en outil de design system.

Plafonds durs

  • 3 concepts maximum par lot, 3 planches maximum par kit.
  • 100 composants par planche, 300 composants par kit.
  • Les planches de composants utilisent toujours GPT-Image-2, « qui se découpe le plus fiablement » — le choix de modèle ne porte que sur les concepts.
  • Coût par image de concept : GPT-Image-2 7 · Nano Banana 2 18 · Nano Banana Pro 24.

§6Post-traitement & édition

Sept opérations attachées à chaque asset, plus un éditeur pixel complet. C'est ce qui distingue un générateur d'images d'un outil de production.

Le découpage se fait par alpha connexe, avec activation automatique d'une isolation « smart alpha » quand les boîtes englobantes se chevauchent. Pour une animation, la détection porte sur l'union de toutes les frames et chaque résultat reste une animation avec son timing d'origine. Trois modes documentés : Auto Detect, Fixed Grid, Custom Selection. En cas de résultat imparfait comme en cas d'erreur, une URL de révision manuelle est renvoyée.

Astuce de coût promue par l'éditeurUne génération contenant 8 personnages coûte le même prix qu'une génération à 1 personnage. Le slicer transforme donc une image en 8 assets — c'est un facteur 8 sur le coût unitaire, et probablement le levier d'économie le plus important du produit.

La règle la plus explicite du serveurNe jamais resoumettre un job en file ou en cours : chaque soumission crée et facture un nouveau job. Le plafond de parallélisme est celui du palier — 5 jobs simultanés sur Adventurer, jusqu'à 10 sur Archmage — lisible via get_credit_balance.

§10Règles métier

Récapitulatif des contraintes dures, celles qui produiraient une erreur si on tentait de les violer.

Exclusions mutuelles et conditions

  • Détourage : fournir exactement un des deux — un asset_id ou une image inline.
  • Export Godot d'un personnage : fournir un run_id ou une liste d'assets d'animation. Aucun champ n'est déclaré obligatoire dans le schéma — l'échec ne survient qu'à l'exécution.
  • Le paramètre de palette d'une animation n'est valide qu'en mode pixel.
  • Arêtes two_surfaces : tilesets top-down 15-piece uniquement.
  • Fournir un concept déjà possédé à la création d'un UI kit saute les étapes de génération et de sélection de concept.
  • Ne préciser ni animations préréglées ni animations personnalisées déclenche les défauts de la perspective.

Prérequis d'entrée

  • Animer exige impérativement un asset possédé — les octets inline sont refusés.
  • Finaliser un UI kit exige un brouillon issu de l'extraction, ou une liste de composants corrigés.
  • Exporter un personnage exige un run terminé.
  • Générer des animations exige la même perspective que le personnage de base.
  • Le jeton d'upload est éphémère : la fenêtre de transfert est bornée dans le temps.

§11Lecture critique

Ce qui, dans cette conception, mérite d'être repris — et ce qui ne tient pas.

Les cinq idées à retenir

  1. Le graphe de dépendances de poses. Insérer des générations intermédiaires déclarées côté serveur, plutôt que d'espérer qu'un modèle d'image comprenne « marche de dos », est la solution la plus économique au problème le plus difficile du domaine. Le graphe est explicite, chaînable, et facturé à part.
  2. La validation en contexte. Le playground jouable, l'aperçu d'étirement 9-slice, l'aperçu « true size » — à chaque fois, l'utilisateur juge l'asset dans les conditions de son usage réel, pas dans une visionneuse.
  3. L'auto-provisionnement du rangement. Les workflows créent projets et collections en même temps que les assets. La bibliothèque reste structurée sans qu'on ait jamais demandé à l'utilisateur de ranger.
  4. Le coût affiché avant le clic. Chaque bouton porte son prix, recalculé en direct à chaque changement de réglage, avec la remise au volume rendue visible (72 barré, 60 affiché). C'est ce qui rend un modèle à crédits supportable.
  5. La réinjection à quatre portes. Chaque asset de la bibliothèque peut redevenir un point de départ de quatre façons distinctes — réglages, référence, source d'édition, guide de style. La cohérence visuelle est un effet de bord de l'ergonomie.

Les fragilités

  • Aucune validation locale possible côté client. Sur les 43 outils MCP, une seule énumération est déclarée dans le schéma JSON. Toutes les autres valeurs autorisées ne vivent que dans le texte des descriptions. Un client qui se fie au schéma n'a aucun garde-fou ; il doit dupliquer ces listes.
  • Deux surfaces qui divergent. La documentation publique de l'API expose des routes personnages et tilesets que l'écran des scopes de clé, lui, ne liste pas. Le schéma du tileset expose des paramètres absents de sa propre documentation. La surface REST et la surface MCP ne se recouvrent pas exactement.
  • Pas de webhooks. Le polling est la seule voie, sans intervalle recommandé, avec des URL signées qui expirent. Pour une intégration en production, c'est le point le plus coûteux à écrire.
  • Le mode UI est annoncé « bientôt » dans le sélecteur principal alors qu'il est déjà servi par l'API et par le UI Kit Builder. L'incohérence est visible pour l'utilisateur.
  • Aucune limite de débit chiffrée n'est publiée — seul le code 429 est documenté. Impossible de dimensionner une intégration sans tâtonner.
  • La rétention des assets n'est pas documentée. Pour un studio qui bâtit sa production sur l'outil, c'est une question ouverte qu'il vaudrait mieux poser avant d'y investir.

Ce qui a été exécuté pour de vrai

Un parcours Character Creator complet : prompt → style et perspective → génération du sprite de base (≈ 9 s) → écran de révision → sélection de 3 animations → génération (≈ 90 s) → playground → ouverture du dialogue d'export. Aucun fichier n'a été téléchargé. Le UI kit existant du compte a été ouvert en lecture seule pour relever la taxonomie des composants et l'éditeur 9-slice.

Points non vérifiés

  • Contenu exact des archives Unity, Godot, Phaser et Roblox — le dialogue d'export a été ouvert, rien n'a été téléchargé.
  • Prix annuels absolus et composition des packs de crédits top-up : affichés uniquement dans des composants interactifs de facturation.
  • Qualité réelle des tilesets autotile et des textures sans couture : aucun n'a été généré.
  • Comportement du Slicer sur une planche multi-sprites : décrit d'après la documentation et les schémas, non exécuté.

Un écart de 2 crédits

Le test a consommé 74 crédits pour des opérations affichées à 12 + 60 = 72. L'écart de 2 crédits n'a pas été élucidé ; l'hypothèse la plus probable est une facturation résiduelle de la prep de pose ou d'une passe de détourage. Signalé plutôt que masqué.
